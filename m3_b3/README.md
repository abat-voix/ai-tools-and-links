# Фоновый отчёт по заявкам

Маршруты отчётов работают внутри FastAPI-сервиса техподдержки из Б3.1. Обработчик сохраняет задачу в SQLite и сразу возвращает её адрес. Отдельный процесс воркера перечитывает заявки с правами владельца, группирует их по статусу и записывает результат в ту же базу. В отчёте используются демонстрационные заявки сервиса.

## Запуск

Нужны Python 3.12, SQLite с поддержкой `RETURNING` и установленные зависимости сервиса Б3.1. Команды выполняются из `m3_b1`.

В обоих терминалах задать одинаковые пути:

```bash
export PYTHONPATH="$PWD:$(cd ../m3_b3 && pwd)"
export REPORTS_DB="$PWD/report-jobs.sqlite3"
```

В первом терминале запустить API:

```bash
uv run uvicorn support_reports.asgi:app --host 127.0.0.1 --port 8000
```

Вызов маршрутов отчётов использует только демо-токен сервиса. Если нужен запуск без подключения к OpenAI, задать непустое значение-заглушку `OPENAI_API_KEY=offline-placeholder` перед стартом API. С этим значением доступны отчёты, обработка чата требует действующего ключа.

```bash
curl -i http://127.0.0.1:8000/reports/jobs \
  -H "Authorization: Bearer ${DEMO_TOKEN}" \
  -H "Idempotency-Key: report-support-a-001" \
  -H "Content-Type: application/json" \
  -d '{"ticket_ids":["T-1042"]}'
```

Здесь `DEMO_TOKEN` содержит демо-токен пользователя `support-a` из настроек сервиса. Получить адрес из заголовка `Location`. Пока воркер выключен, `GET` по этому адресу с тем же токеном вернёт `queued`.

Во втором терминале запустить воркер:

```bash
uv run python -m support_reports.worker
```

Флаг `--once` обрабатывает одну доступную задачу и завершает процесс. Воркер вводит двухсекундную задержку, чтобы было видно состояние `running`. После завершения `GET /reports/jobs/{job_id}` вернёт `status: succeeded` и `result: {"requested":1,"by_status":{"in_progress":1}}`.

## Контракт повторов

- `POST /reports/jobs` принимает от 1 до 20 разных заявок и заголовок `Idempotency-Key`. Ответ `202` содержит `job_id`, `status`, `result`, `error` и адрес проверки в `Location`.
- Тот же ключ и тот же набор заявок пользователя возвращают прежнюю задачу в её текущем состоянии. Порядок идентификаторов не влияет на сравнение. Повтор ключа с другим допустимым набором возвращает `409`.
- Неизвестные и чужие заявки возвращают `404`. `GET` отдаёт состояние и результат только владельцу задачи.
- Воркер захватывает задачу на 15 секунд. Если процесс остановился, новый воркер заберёт задачу после истечения срока. Результат записывается только с токеном текущей попытки в пределах её срока. После трёх истёкших попыток воркер переведёт задачу в `failed`.

Для учебного запуска достаточно одного процесса API и одного воркера, которые используют SQLite-файл на одном компьютере. Работа воркера только читает синтетические заявки, поэтому повторное выполнение безопасно. Задачи остаются в базе между запусками. Для сервиса с постоянной нагрузкой нужны очистка истории задач, мониторинг очереди и выбор хранилища по результатам замеров.

## Проверка

Из каталога сервиса Б3.1 с тем же `PYTHONPATH`:

```bash
uv run python -m pytest -q ../m3_b3/tests
uv run ruff check ../m3_b3
```

Тесты используют временную SQLite-базу и поднимают маршруты через `httpx.ASGITransport`.
